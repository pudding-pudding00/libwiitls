# libwiitls 1.1.0 – Umsetzungsplan (Master-Plan)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Alle Punkte der Roadmap aus Issue #7 in abhängigkeitsgerechter Reihenfolge umsetzen und als SemVer-kompatibles 1.1.0 veröffentlichen.

**Architecture:** Das Kernstück ist eine nicht-blockierende HTTP-State-Machine (`wtls_http_start()`/`wtls_http_step()`), auf die der bestehende blockierende Pfad (`wtls_http_open()`) als dünne Schleife umgestellt wird – damit gibt es *einen* Codepfad, den die vorhandene `http`-Suite absichert. Asynchrones DNS, Gesamt-Deadline/Retry und HTTP/2-Multiplexing bauen darauf auf. Updater-Funktionen (Signaturprüfung → Download-Helfer → Laufzeit-CA-Bundle) nutzen ausschließlich PSA-Krypto, die schon im Build ist; es entsteht keine neue handgeschriebene Kryptografie.

**Tech Stack:** C11, CMake ≥ 3.20, Mbed TLS 4.1 LTS + TF-PSA-Crypto, zlib, libogc/devkitPPC, Python 3 (Testserver, Generatoren), Clang/libFuzzer, GitHub Actions (+ QEMU für Big-Endian).

**Spec:** GitHub-Issue #7 „Roadmap: libwiitls 1.1.0“ (https://github.com/pudding-pudding00/libwiitls/issues/7). Ergänzend: `CONTRIBUTING.md` (Code-/ABI-Regeln), `docs/usage.md` §12 (Versionierung).

### Scope-Hinweis

Das Issue umfasst ~25 voneinander weitgehend unabhängige Teilsysteme. Ein einziger Schritt-für-Schritt-TDD-Plan dafür wäre länger als der Code. Dieses Dokument ist deshalb ein **Master-Plan**: Es legt Reihenfolge, Abhängigkeiten, alle API-Entscheidungen (exakte Signaturen), Dateien, Testnamen und Abnahmekriterien je Arbeitspaket (WP) fest. **Vor dem Start jedes WPs** wird daraus mit `superpowers:writing-plans` ein eigener, feingranularer Plan `docs/superpowers/plans/<datum>-wtls-<wp>.md` erstellt (und idealerweise je WP ein Unter-Issue von #7). Ausnahme: WP0 ist klein und hier bereits voll ausformuliert.

## Global Constraints

- SemVer 1.x: keine entfernten/geänderten Funktionen, Fehlercodes oder Struct-Felder; neue Felder **nur am Ende** von `wtls_options`, `wtls_http_request`, `wtls_http_info`; Wert 0 = Verhalten von 1.0.
- Ausnahmen vom „kein geändertes Default-Verhalten“ werden in `CHANGELOG.md` unter `### Changed` explizit genannt (in diesem Plan: nur „`abort_cb` wirkt jetzt auch während DNS im blockierenden `wtls_connect()`“, WP2).
- Single-Thread-Regel für die öffentliche API bleibt: jede `wtls_*`-Funktion aus *einem* Thread. Interne Threads gibt es nur im DNS-Resolver (WP2); sie berühren keinen globalen Zustand außer ihrer eigenen, per Mutex geschützten Request-Tabelle.
- Neue Fehlercodes (in `wiitls.h`, mit Text in `wtls_strerror()`): `WTLS_ERR_UNSUPPORTED = -14` (Funktion wegkompiliert), `WTLS_ERR_WS = -53` (WebSocket-Protokollfehler), `WTLS_ERR_FILE = -60` (Datei-I/O), `WTLS_ERR_INTEGRITY = -61` (Digest oder Signatur falsch).
- Funktionen, die per CMake-Option abschaltbar sind, existieren immer als Symbol und liefern dann `WTLS_ERR_UNSUPPORTED` (ABI bleibt gleich, egal wie gebaut).
- C11, `-Wall -Wextra` ohne neue Warnungen; Präfix `wtls_`, `snake_case`, 4 Leerzeichen.
- Geheimnisse mit `mbedtls_platform_zeroize()` löschen; Code mit Geheimnissen constant-time.
- **Keine neue handgeschriebene Kryptografie** (Non-Goal). Signaturen = ECDSA P-256 über PSA.
- TLS-only-Programme dürfen keinen HTTP-Code linken (bestehende Tests `http_not_linked_into_tls_only` u. a.); jedes neue Modul (Download, WebSocket, Cookie, Logging-Formatierer) bekommt einen eigenen `check_no_symbol`-Linktest.
- Tests für Host *und* Wii liegen in `tests/common/`; Host-Einstieg in `tests/host/test_<suite>.c`, Wii-Suite in `tests/hw/suites.inc`.
- Jede nutzer-sichtbare Änderung: Zeile in `CHANGELOG.md` `[Unreleased]`, Abschnitt in `docs/usage.md`, Doxygen-Kommentar im Header.
- Größenrelevante Optionen (Brotli, zstd, Keylog) sind standardmäßig `OFF`.
- Versionsbump zum Release: `project(... VERSION 1.1.0)` in `CMakeLists.txt` **und** `WTLS_VERSION_MINOR 1`, `WTLS_VERSION_PATCH 0`, `WTLS_VERSION "1.1.0"` in `include/wiitls/wiitls.h` (wird beim Configure verglichen).

## Review Focus

1. **Abbruch mitten in einer asynchronen Anfrage** (`wtls_http_close()` während `WTLS_WANT_*`, `abort_cb` während DNS/Connect/Handshake/Body): kein Leak, kein halb benutzter Socket im Keep-Alive-Pool, bei HTTP/2 nur `RST_STREAM` für diesen Stream. → Tests in WP3/WP12 (`http_async_close_while_pending_*`, `h2_mux_cancel_one_stream`).
2. **Teil-Datei nach Stromausfall, Server ignoriert `Range` oder Datei hat sich geändert** (anderes `ETag`): nie fremde Bytes anhängen, sondern bei 0 neu beginnen; `.part` größer als die Gesamtlänge → verwerfen. → Tests in WP4 (`download_resume_etag_changed_restarts`, `download_part_larger_than_total_restarts`).
3. **Netzwechsel während laufender Lookups/Streams** (`wtls_net_reset()` oder geänderte `net_gethostip()` während async DNS oder Multiplexing): laufende DNS-Ergebnisse werden verworfen statt gecacht, Streams scheitern sauber mit `WTLS_ERR_IO`. → Tests in WP2 (`dns_async_result_dropped_after_net_reset`) und WP12.
4. **Allocator nach `wtls_init()` gesetzt** oder `NULL`-Rückgabe des Allokators mitten im Handshake: `WTLS_ERR_STATE` bzw. sauberes `WTLS_ERR_NOMEM` ohne Leak/Doppel-Free. → Tests in WP5 (`alloc_set_after_init_refused`, `alloc_fail_nth_*`).
5. **HTTP/2-Server mit `SETTINGS_MAX_CONCURRENT_STREAMS = 0`/Absenkung während der Verbindung, `GOAWAY` mit laufenden Streams:** Anfragen warten bzw. werden auf eine neue Verbindung gelegt; nur Streams > `last_stream_id` werden wiederholt, und nur wenn idempotent. → Tests in WP12 (`h2_mux_max_streams_zero_queues`, `h2_mux_goaway_retries_above_last_id`).

## Reihenfolge und Meilensteine

```
M0  WP0  ABI-Wächter + neue Fehlercodes
M1  WP1  Logging/Keylog ─────────────┐   WP5 Allocator-Hooks      (parallel)
    WP6  Dolphin-Messung (parallel)  │   WP7 Differential-Fuzzing + Wycheproof
    WP8  HTTP/2- + HPACK-Fuzzer  ────┼── (muss vor WP3b fertig sein: Refactor unter Fuzz-Schutz)
M2  WP2  Async DNS ──► WP3a Async HTTP/1.1 ──► WP3b HTTP/2 nicht-blockierend ──► WP9 Deadline/Retry
M3  WP4  Signaturprüfung ──► WP10 Download-Helfer ──► WP11 CA-Bundle zur Laufzeit (+ signiert)
M4  WP12 HTTP/2-Multiplexing (braucht WP3b)   WP13 WebSocket (braucht WP3a)
    WP14 Mehr SPKI-Pins   WP15 Record-Buffer
M5  WP16 Mbed-TLS-Patches reduzieren (jederzeit parallel; externe Abhängigkeit Upstream)
M6  WP17–WP25 Priorität 3 (Auswahl; Rest auf 1.2 verschieben)
M7  WP26 Release 1.1.0
```

**Release-Schnitt (Empfehlung):** Priorität 1 (WP1–WP7, WP10) ist Pflicht für 1.1.0, Priorität 2 „soll“, Priorität 3 nur, was bis zum Feature-Freeze fertig ist. HTTP/2-Multiplexing (WP12) ist der größte Risikoposten; rutscht er, bleibt das sequentielle HTTP/2 aus 1.0 unverändert und 1.1.0 erscheint trotzdem.

**Entscheidungen, die dieser Plan trifft** (Begründung im jeweiligen WP):
- Async-HTTP: **Option A** (State-Machine). Option B (Netzwerk-Worker) wird nur als Beispielprogramm geliefert, nicht als API.
- Async DNS auf der Wii: Resolver-LWP um `net_gethostbyname()`, nicht eigener UDP-Stub-Resolver.
- Async DNS in `wtls_connect_start()`: **Opt-in** über neues Feld `wtls_options::async_dns`, weil `wtls_get_fd()` in der DNS-Phase `-1` liefern muss und bestehende Poll-Schleifen das sonst als Fehler sehen könnten.
- Signaturen: **ECDSA P-256**, nicht Ed25519 (Ed25519 fehlt im TF-PSA-Crypto-Builtin-Treiber und wäre neue handgeschriebene Krypto).

### WP7: Differential-Tests der Krypto-Beschleuniger + Wycheproof (Prio 1)

**Files:** Create `tests/fuzz/fuzz_x25519_diff.c`, `tests/fuzz/fuzz_p256_verify_diff.c`, Korpora `tests/fuzz/corpus/x25519_diff/`, `.../p256_verify_diff/`, `tools/gen_wycheproof.py`, `tests/common/wycheproof_x25519.inc`, `tests/common/wycheproof_p256.inc` (generiert, nicht von Hand editieren); Modify `tests/common/crypto_tests.c`, `CMakeLists.txt`, `.github/workflows/ci.yml`.

**Aufbau:** Die Fuzz-Builds konfigurieren Mbed TLS mit `-DWTLS_ACCEL=OFF -DWTLS_ACCEL_P256=OFF` (Referenz = unveränderte Mbed-TLS/TF-PSA-Implementierung) und kompilieren `src/accel/x25519_fe32.c` / `src/accel/p256_verify.c` direkt in den Harness. Vergleich:
- X25519: `wtls_x25519(out, scalar, point)` vs. PSA `psa_raw_key_agreement(PSA_ALG_ECDH, …)` mit Montgomery-255-Schlüssel; gleiche Ausgabe, inkl. All-Zero-Ergebnis bei Low-Order-Punkten, nicht-kanonischen u-Koordinaten (≥ 2²⁵⁵−19) und gesetztem Bit 255.
- P-256: `wtls_p256_verify(pub, hash, …)` vs. `psa_verify_hash(…, PSA_ALG_ECDSA(PSA_ALG_SHA_256), …)`; identisches Akzeptieren/Ablehnen für r/s = 0, = n, > n, Punkte nicht auf der Kurve, Punkt im Unendlichen, Hash mit gesetzten hohen Bits.
- Eingabeformat des Harness: erstes Byte wählt den Modus (zufällig / kanonisierte Grenzwerte), damit der Fuzzer gezielt Randfälle trifft.

```c
/* Wie wtls_http_open(), aber kehrt nie blockierend zurück. WTLS_OK: Antwortkopf da;
 * WTLS_WANT_READ/WTLS_WANT_WRITE: *out gesetzt, mit wtls_http_step() weitertreiben;

 * WTLS_OK/Fehler gültig bleiben (anders als bei wtls_http_open()). */
```

```c
void wtls_h2_reset_stream(wtls_h2_conn *c, uint32_t sid);       /* RST_STREAM(CANCEL), Verbindung bleibt */
uint32_t wtls_h2_goaway_last_id(const wtls_h2_conn *c);         /* UINT32_MAX solange kein GOAWAY */
/* wtls_http_pool.h */
void *wtls_http_pool_share_h2(bool secure, const char *host, uint16_t port, bool insecure,
                              bool has_cred, const uint8_t *cred_fp, uint64_t now_ms); /* Verbindung mit freiem Stream-Slot oder NULL */
```
**Regeln:** Limit = `min(SETTINGS_MAX_CONCURRENT_STREAMS des Servers, WTLS_H2_MAX_STREAMS)`. Empfangspuffer je Stream ≤ Stream-Fenster (initial 64 KiB, `SETTINGS_INITIAL_WINDOW_SIZE`), `WINDOW_UPDATE` erst wenn der Aufrufer liest ⇒ Speicher pro Verbindung ≤ `WTLS_H2_MAX_STREAMS × 64 KiB + Record-Buffer`. DATA-Versand Round-Robin über Streams mit Sendebedarf, max. 1 Frame (≤ 16 KiB) pro Stream und Runde. Früher `wtls_http_close()` ⇒ `RST_STREAM` nur dieses Streams. `GOAWAY` ⇒ Streams > `last_stream_id` werden bei idempotenten Methoden auf eine neue Verbindung gelegt, sonst `WTLS_ERR_IO`. Blockierendes `wtls_http_open()`/`wtls_http_fetch()` unverändert (ein Stream).

**Tests:** `h2_mux_two_streams_one_connection` (`wtls_http_get_info().reused_connection` beim zweiten; Testserver zählt genau 1 TLS-Verbindung), `h2_mux_interleaved_data_correct`, `h2_mux_large_does_not_starve_small` (10-MiB-Stream + 1-KiB-Stream: der kleine ist fertig, bevor der große 10 % hat), `h2_mux_cancel_one_stream` (anderer Stream läuft weiter, Server sieht `RST_STREAM` mit Fehlercode `CANCEL`), `h2_mux_max_streams_zero_queues` (Review Focus 5), `h2_mux_server_limit_lowered`, `h2_mux_goaway_retries_above_last_id`, `h2_mux_goaway_post_fails_io`, `h2_mux_memory_bounded` (Zähl-Allokator aus WP5: Spitzenwert ≤ berechnete Grenze); Soak: 200 Requests auf 4 Streams ohne Leak. Fuzzer aus WP8 laufen gegen die neue Engine.

**Abnahme:** zusätzlich `bench`: 16 kleine Requests an einen Host über die Async-API schneller als sequentiell in 1.0.1 (Zahlen in `docs/benchmarks.md`).
